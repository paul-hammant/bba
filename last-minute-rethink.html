Here is the same idea told as a change you already merged and expected to ship, but have started to regret. Every other telling on this site starts before the work does, with someone weighing up how to begin something long. This one starts too late for that. The algorithm has been rewritten, the commit is merged, the release branch is cut with that commit among a series of changes, but the final build has not been made. A week before go-live somebody says the thing nobody wants to hear: I am not sure we got that right.

1. The change that seemed finished

A lending team is asked to correct how loan amortization is calculated. The existing schedule is a straight-line split: the principal is divided evenly across the term, and interest is charged on what is left. Finance want the industry-standard annuity method instead, where the monthly payment is constant and the split between interest and principal moves over the life of the loan. It is a real change with a real justification, and there is a regulation cited in the ticket.

One developer picks it up. It is not a months-long migration — it is one class, a formula, and a fortnight. Nobody involved thinks this needs branch by abstraction, and on the day, nobody is wrong about that. The commit replaces the old formula with the new one.

Eleven lines. That is worth dwelling on for a second, because the size of that diff is exactly why nobody reached for branch by abstraction on the day, and it is also why the regret in the next section is so awkward: there is no obvious seam in it. The change is not additive. It rewrites the variables in place — perMonth becomes growth, and payment moves from being computed per-month to being computed once up front. You cannot keep both behaviors by keeping both halves of this diff, which is what makes the naive "just put an if around it" answer fail.

The same commit touched the test file too, and that part is not shown above — picture a seven-line test method swapped out for a slightly longer nine, because the expected numbers all moved and the annuity method wants an extra assertion or two to pin the payment being constant. Nothing surprising, and at review time nobody would look twice at it. But it is the more consequential half of the commit for what happens next. The old behavior is now absent from the test suite as well as from the codebase, which means nothing in CI is watching it any more. When section 3 goes back for it, the expectations have to be recovered from history alongside the implementation.

2. The regret, which is not yet a decision

Six days before go-live, someone reads the regulation again and says the annuity method may be correct in general but wrong for the fixed-term products that make up most of the book, because of how early settlement is rebated. They are not certain. The person who could settle it is on leave until after the release.

Notice the shape of this problem. It is not "the new code is broken" — if it were, you would revert abab33f and be done in a minute. It is "the new code may be answering a question we have asked wrongly, and we will not know for a fortnight." Those two look similar at 5pm on a Thursday and they are not the same thing at all.

The obvious moves are all bad in the same way, which is that each of them makes the decision now, on behalf of somebody who is not in the room:

  • Revert it — or, as someone might have said before modern VCS terminology settled, unmerge it. But where? Revert it on trunk and cherry-pick that revert to the release branch, and the annuity work disappears from the continuing line of development too. Revert it only on the release branch, and the team has created a difference that somebody must remember and reconcile later. Either way, if the original rationale was right after all, the next move is a revert-of-the-revert under more pressure.
  • Ship it and watch. Also cheap today. If it is wrong, you have mis-stated the interest split on live loan accounts, and the fix is not a deploy, it is a remediation letter.
  • Hold the release. The rest of the drop — everything else the team finished this quarter — now waits on one unavailable reviewer's opinion about one formula.
  • Branch it off and decide later. The classic. Cut another branch with the old formula restored, keep it alive until the answer arrives, then merge whichever one wins. But this commit sits in the middle of other work, and the amortization code will not necessarily stand still while the answer is pending. Every intervening rounding fix or fee-handling change then has to be understood and applied across two divergent lines.

What the team actually wants is to not decide yet, and to make not-deciding cost almost nothing. That is what the abstraction buys. Every other page on this site introduces the abstraction to make a long change survivable while it is in progress. Here the change is already finished, and the abstraction is introduced to make a finished change reversible in production without a code change.

3. Resurrect the old algorithm as a peer, not as a revert

The next commit does not undo abab33f. It goes to the commit's parent, lifts the old formula back out of history, and gives both formulas a name and a shared shape. The wording in the commit message is deliberate — resurrect, not revert — because the old code is coming back as a living peer of the new one, both compiled, both tested, both shippable.

7c41e0d   Resurrect straight-line amortization behind an abstraction, toggled at boot
Merged on trunk, then cherry-picked to the already-cut release branch. No behavior change by default.

First, the seam. It is the smallest interface that both implementations can honestly satisfy, which in this case is the method that already existed:

package com.mycompany.lending;

import java.util.List;

public interface AmortizationSchedule {

    List<Installment> scheduleFor(Loan loan);
}

Then the old algorithm, recovered from abab33f^ — the state of the file immediately before the change — and renamed. Not rewritten from memory, and not reconstructed from the ticket. Taken out of git verbatim, so that it is exactly the behavior that is live in production today:

public class StraightLineAmortizationSchedule implements AmortizationSchedule {

    private static final int SCALE = 2;
    private static final RoundingMode HALF_UP = RoundingMode.HALF_UP;

    @Override
    public List<Installment> scheduleFor(Loan loan) {
        List<Installment> installments = new ArrayList<>();
        BigDecimal rate = loan.monthlyRate();
        BigDecimal perMonth = loan.principal()
                .divide(BigDecimal.valueOf(loan.termInMonths()), SCALE, HALF_UP);

        BigDecimal balance = loan.principal();
        for (int month = 1; month <= loan.termInMonths(); month++) {
            BigDecimal interest = balance.multiply(rate).setScale(SCALE, HALF_UP);
            BigDecimal payment = perMonth.add(interest);
            balance = balance.subtract(perMonth);
            installments.add(new Installment(
                    month, payment, interest, perMonth, balance.max(BigDecimal.ZERO)));
        }
        return installments;
    }
}

And the new algorithm, which is the body of abab33f moved across unchanged. This is a rename and an implements clause, nothing more. If the diff for this file shows anything else, the commit is doing too much:

public class AnnuityAmortizationSchedule implements AmortizationSchedule {

    private static final int SCALE = 2;

    @Override
    public List<Installment> scheduleFor(Loan loan) {
        // ... body moved verbatim from abab33f, not retyped ...
    }
}

4. One toggle, read once at boot

The choice is made in exactly one place. Not at each call site, not per request, and not inside either implementation — neither algorithm knows the other exists, and neither has an if in it:

public class ReleaseToggles {

    private final boolean annuityAmortization;

    public ReleaseToggles(Config config) {
        this.annuityAmortization = config.getBoolean("toggles.annuityAmortization");
    }

    public AmortizationSchedule amortizationSchedule() {
        return annuityAmortization
                ? new AnnuityAmortizationSchedule()
                : new StraightLineAmortizationSchedule();
    }
}

Wired in at composition time, so that everything downstream keeps holding an AmortizationSchedule and stays entirely unaware that there is a question outstanding:

public class LendingModule {

    public LoanService loanService(ReleaseToggles toggles, LoanRepository repository) {
        return new LoanService(repository, toggles.amortizationSchedule());
    }
}

toggles {
  # September drop ships on the resurrected straight-line method while the
  # annuity rationale is confirmed. Flip to true to switch; delete both this
  # and the loser once the answer lands. See BBA-1140.
  annuityAmortization = false
}

That default is the whole point of the exercise. When the final build is made, the release will contain the behavior that is already live, which is the conservative choice, and it will contain it having been chosen rather than having been reverted to. The annuity code will still be in the final binary; it is still compiling, still under test, and one config line away. Nobody has to decide yet, and the release does not have to wait.

QA may enjoy this arrangement more than the developer does. During release testing they can exercise both choices, and at the last minute they can select the old, existing behavior in release config without asking a developer to change code or prepare another build. That is the kind of control that prevents uncertainty late in release week from turning into another eighteen-hour day.

For the developer, branch by abstraction can feel like an irritating amount of extra typing after the real work was supposedly finished: recover the old code, name two implementations, extract an interface, wire a toggle and restore tests. The optionality can feel alien too, because it asks them to preserve the possibility that their completed change — reviewed, merged and believed correct — may not be the behavior the business finally chooses. That discomfort is real. It is also the small, visible cost being exchanged for QA not having to improvise a code change during the release.

By the way: boot-time toggles versus hot switches

"One config line away" is doing some quiet work in that sentence, though, because it does not say how far away. Toggles come in more than one flavour, and the choice between them is a separate decision from the one this page has been making:

  • Boot-time toggles are read once as the process starts, which is what the ReleaseToggles constructor above does. Changing your mind means editing config and restarting the stack — a deploy, or at least a rolling bounce. In exchange, the value cannot change underneath a request, every instance in the fleet is unambiguously on one side or the other, and a stack trace from production tells you which implementation ran.
  • Hot switches are read at the point of use, so ops or an admin can flip them in the running stack — an admin screen, a feature-flag service, a watched config key — with no restart and no deploy. The switch takes effect in seconds, and it can be flipped back just as fast at three in the morning by somebody who was not involved in writing either implementation.

For the seam itself, the difference is small: the abstraction does not care who is asking or how often. It is the composition that moves. A boot-time toggle can hand the chosen implementation to LoanService once at startup, as above. A hot switch cannot, because the answer has to be allowed to change after startup — so the toggle is consulted per call instead, and the thing injected downstream becomes the chooser rather than the choice:

public class SwitchableAmortizationSchedule implements AmortizationSchedule {

    private final LiveToggles toggles;
    private final AmortizationSchedule annuity = new AnnuityAmortizationSchedule();
    private final AmortizationSchedule straightLine = new StraightLineAmortizationSchedule();

    @Override
    public List<Installment> scheduleFor(Loan loan) {
        // Re-read per call - that is the whole difference from ReleaseToggles,
        // whose field is final and set once in the constructor.
        AmortizationSchedule chosen = toggles.isOn("annuityAmortization") ? annuity : straightLine;
        return chosen.scheduleFor(loan);
    }
}

Note what that class is and is not. It is still one decision in one place — it is not an if sprinkled through the call sites, which is the thing this whole site exists to argue against. Both implementations remain ignorant of each other, and it gets deleted in section 6 along with everything else. What it does add is a second thing to get right: LiveToggles is now read on every call from somewhere that another thread can change, so it has to be cheap and it has to be safe to read concurrently. A boot-time final field is neither of those problems.

Which one suits this story? Probably the boot-time toggle, and it is worth being clear why, because the hot switch is the more impressive-sounding option. The team here is waiting on a reviewer to settle a question of correctness, not watching a dashboard for a bad rollout. Nobody is going to need to flip this at 3am. And an amortization schedule is not a thing you want changing between two loans in the same batch: mid-flight switching means two loans processed a second apart get different interest splits, and reconciling that afterwards is worse than the restart you avoided.

The hot switch earns its keep on the other kind of change — the long migration the rest of this site describes, where you are moving live traffic onto a new implementation and want to be able to back it out in seconds when the error rate climbs, without waiting for a deploy. Same abstraction, same deletion at the end; only the wiring differs.

5. Both implementations stay guarded by CI

Two implementations means twice the tests, and this is the cost you accept in exchange for the option. The test that abab33f rewrote gets its old expectations back — again lifted from history rather than re-derived — and both are now run against their own implementation, with a third test that pins the toggle itself:

public class AmortizationScheduleTest {

    private static final Loan LOAN = new Loan("10000.00", "0.06", 12);

    @Test
    public void straightLineSplitsPrincipalEvenly() {
        List<Installment> schedule =
                new StraightLineAmortizationSchedule().scheduleFor(LOAN);
        assertEquals("833.33", schedule.get(0).principal().toString());
        assertEquals("833.33", schedule.get(11).principal().toString());
    }

    @Test
    public void annuityHoldsThePaymentConstant() {
        List<Installment> schedule =
                new AnnuityAmortizationSchedule().scheduleFor(LOAN);
        assertEquals("860.66", schedule.get(0).payment().toString());
        assertEquals("860.66", schedule.get(11).payment().toString());
    }

    @Test
    public void septemberDropUsesStraightLine() {
        ReleaseToggles toggles = togglesWith("annuityAmortization", false);
        assertThat(toggles.amortizationSchedule(),
                instanceOf(StraightLineAmortizationSchedule.class));
    }
}

Suppose a rounding fix and a fee-handling change land on trunk while the reviewer is away. Shared changes go into shared code; behavior-specific changes go into the implementation they concern. They do not have to be ported between two branches whose only purpose is to preserve the two possible answers. That repeated reconciliation is the cost the branch alternative was quietly promising to charge.

6. Delete the loser and the abstraction with it

The reviewer eventually comes back and settles it — whichever way. That may be weeks or months after this release, and the cleanup can happen later on trunk without keeping a release branch alive or reconciling two divergent versions in the meantime. The follow-up work is the same either way and it is not optional: flip the toggle if the answer is annuity, let it run, then delete the losing implementation, delete the toggle, delete its config entry and its test, delete the switcher class if you took the hot-switch route, and collapse the interface back into the one surviving class. There is no deadline imposed by this release; the modest cost of waiting is that CI must keep guarding both implementations and people must continue to understand why the temporary choice exists. That deletion is the merge back. A team that leaves the abstraction standing "in case we want to switch again" has not finished the job; it has swapped a temporary period of branch divergence for a permanent fork in the codebase, and the next person to read it will not know which side is the real one.

Worth being honest about what this telling is not. Branch by abstraction did not save the team from a long migration here, because there was not one. It saved them from having to be certain on a Thursday. The abstraction may exist for weeks or months before it is deleted, and its entire value is that period of not-yet-deciding it buys at a cost of one interface, one toggle, and an additional CI path for as long as both implementations remain.

Epilogue: automate the mechanical part

Now read back what commit 7c41e0d actually did. Every step of it is mechanical. Go to a commit's parent. Take the file as it stood. Give both versions a name. Extract the interface they already share. Put the choice behind a toggle read once at startup. Restore the old expectations into the test suite. Default to the incumbent. None of it required judgement about amortization at all — the judgement was in noticing the regret, and that part is still yours.

Which raises a question this site is not too proud to ask out loud. What if the whole of section 3, 4 and 5 were one prompt to a coding agent?

> Redo commit abab33f as an abstraction of old and new, as described in http://branchbyabstraction.com/last-minute-rethink.html

That is about as self-referential as a page about branch by abstraction can get: a document whose last section asks to be pasted into a coding agent as the specification for the change the rest of the document just described by hand. If it works, the initial mechanical setup for those weeks or months of optionality costs about ninety seconds, and the calculation in section 2 changes for every team that ever shipped something and then had second thoughts about it on the Thursday.

Two caveats, because the joke should not eat the point. The first is that an agent doing this well has to lift the old implementation out of git rather than reconstruct it from the ticket — a plausible-looking reimplementation of the old formula is worse than useless here, because the entire reason to resurrect it is that it is exactly what is running in production today. The second is section 6. The deletion is the part that a prompt will not remind you about, and it is the part that separates branch by abstraction from a codebase slowly filling up with toggles that nobody dares remove.
